# mattermost-mcp: публичный релиз 1.0 — дизайн

Дата: 2026-10-30

## Зачем

Сервер написан для собственного агента (Гермес): только чтение, авторизация
куками браузера (`MMAUTHTOKEN`/`MMCSRF`), ставится из git-клона. Теперь его
нужно отдать сообществу как полноценный MCP-сервер для Mattermost, которым
человек может пользоваться «из коробки»: поставить одной командой, дать
обычный токен, читать и — если разрешил — писать.

Ниша, которую мы занимаем (по обзору существующих серверов): аккуратный,
безопасный по умолчанию сервер с лучшими в классе инструментами чтения
(непрочитанное как в клиенте, муты, категории сайдбара, упоминания), плюс
единственная нормальная поддержка куки-авторизации для серверов, где PAT
выключены или прокси срезает `Authorization`.

## Цели

1. Авторизация персональным токеном (PAT) или токеном бота, а не только куками.
2. Запись: отправить сообщение, ответить в тред, написать в личку, отредактировать
   **своё** сообщение, поставить/снять реакцию. Включается отдельной настройкой;
   по умолчанию сервер только читает.
3. Дополнительные инструменты чтения, без которых сервер не «полноценный».
4. Исправить найденные ошибки и узкие места по производительности.
5. Оформление и документация уровня публичного проекта; пакет на PyPI,
   готовность к публикации в реестрах MCP.

## Не цели

- HTTP/remote-транспорт, Docker, многопользовательский режим, OAuth — позже.
- Удаление сообщений, создание/архивация каналов, админские операции.
- Загрузка файлов (upload). Чтение метаданных файлов — да.
- Вход через браузер/Playwright, логин по паролю.

## Анти-цели (провал, даже если «работает»)

- **Сломан контракт для Гермеса.** Любая существующая конфигурация (env,
  cookie host, keychain) должна продолжать работать без изменений, восемь
  существующих инструментов — те же имена, те же параметры, те же поля ответа.
- **Запись возможна без явного разрешения.** При выключенной записи агент не
  должен иметь ни инструмента, ни технической возможности что-либо изменить.
- Агент может отредактировать чужое сообщение (даже если у пользователя есть
  права админа на это).
- Секреты (токены, куки) попадают в логи, stdout или тексты ошибок.

## Ограничения

- Python ≥ 3.11, FastMCP (в lock-файле сейчас 4.1.x), httpx, uv. Стек не меняем.
- stdout — канал MCP stdio; диагностика только в stderr.
- Тесты не ходят в сеть и не вызывают ssh (respx-моки), как сейчас.
- Публикация в PyPI, реестр MCP и PR в awesome-mcp-servers — внешние действия
  от имени владельца; мы всё готовим, но сами не публикуем без отдельного «да».

## Контракт, который нельзя ломать

**Инструменты** (имена, параметры, значения по умолчанию, ключи в ответе):
`list_channels`, `get_channel_posts`, `get_thread`, `search_posts`,
`get_direct_messages`, `get_mentions`, `get_unread`, `get_user`.

Разрешено: добавлять новые **необязательные** параметры, добавлять новые
ключи в ответы, исправлять поведение, которое явно сломано (см. «Исправления»).
Запрещено: переименовывать, удалять, менять тип/смысл существующего.

**Конфигурация:** все текущие переменные (`MATTERMOST_URL`, `MATTERMOST_TOKEN`
= кука `MMAUTHTOKEN`, `MATTERMOST_CSRF`, `MATTERMOST_USER_ID`,
`MATTERMOST_COOKIE_*`, `MATTERMOST_KEYCHAIN_SERVICE`, `MATTERMOST_TRUST_ENV`,
`MATTERMOST_AUTH_HELP`), порядок источников (env → cookie host → keychain),
перезапрос cookie host на 401 — сохраняются. Команда `mattermost-mcp` и
`python -m mattermost_mcp` продолжают работать.

## Решения

### Авторизация

- Новая переменная **`MATTERMOST_ACCESS_TOKEN`** — PAT или токен бота,
  отправляется как `Authorization: Bearer <token>`.
- Новая переменная **`MATTERMOST_AUTH_MODE`**: `token` | `cookie`. Если не
  задана — `token`, когда найден `MATTERMOST_ACCESS_TOKEN` (в любом источнике),
  иначе `cookie`. Смысл `MATTERMOST_TOKEN` не меняется (это кука); угадывать
  режим по наличию/отсутствию CSRF нельзя.
- `MATTERMOST_ACCESS_TOKEN` резолвится теми же источниками: env → cookie host →
  keychain (аккаунт `access_token`). В cookie host добавить ключ в белый список.
- В токен-режиме куки и `X-CSRF-Token` не отправляются; повторный перезапрос
  cookie host на 401 работает так же (токен мог быть ротирован там же).
- Первый вызов делает `/users/me`; на 401 — понятная ошибка, текст которой
  зависит от режима (для токена: «токен неверен/отозван, создайте новый в
  Profile → Security → Personal Access Tokens»). Текущий текст для кук и
  `MATTERMOST_AUTH_HELP` сохраняются.
- Значения токенов никогда не выводятся.

### Режим записи

- Переменная **`MATTERMOST_ENABLE_WRITE`** (`1/true/yes/on` включает; по
  умолчанию выключено).
- Выключено → инструменты записи **не регистрируются** (агент их не видит),
  и HTTP-клиент отказывает в любом запросе, кроме GET и белого списка
  читающих POST (`/users/ids`, `/teams/{id}/posts/search`, `/channels/direct`
  — последний создаёт DM-канал при чтении личек, как сейчас, `/users/search`).
  Двойная защита: даже ошибка в коде инструмента не превратится в запись.
- Включено в cookie-режиме без `MATTERMOST_CSRF` → понятная ошибка при первом
  вызове записи (Mattermost требует CSRF для изменяющих запросов с куками).
- Инструменты записи:
  - `create_post(channel_id, message, root_id=None)` — сообщение в канал или
    ответ в тред.
  - `send_direct_message(username, message)` — открывает DM при необходимости.
  - `update_post(post_id, message)` — только если `post.user_id == me.id`,
    иначе отказ с объяснением; через `PUT /posts/{id}/patch`.
  - `add_reaction(post_id, emoji)` / `remove_reaction(post_id, emoji)` — от
    своего имени. `emoji` — имя без двоеточий (`thumbsup`), двоеточия срезаем.
  - Ответ — созданный/изменённый пост в том же формате, что и при чтении.
- Аннотации MCP: чтение — `readOnlyHint=true, idempotentHint=true`; запись —
  `readOnlyHint=false, destructiveHint=false`; `create_post` /
  `send_direct_message` не идемпотентны, `update_post` и реакции — идемпотентны.

### Новые инструменты чтения

- `get_me` — текущий пользователь (и режим: token/cookie, запись вкл/выкл —
  чтобы агент понимал свои возможности).
- `list_teams`.
- `get_post(post_id)`.
- `get_channel(channel_id=None, team_id=None, name=None)` — по ID или по
  имени в команде (агенты знают «town-square», а не ID).
- `search_users(term, limit=20)`.
- `get_pinned_posts(channel_id)`.
- `get_file_info(file_id)` — имя, размер, тип, ссылка; содержимое не качаем.
- `get_channel_posts` и `get_direct_messages`: новый необязательный параметр
  `before` (ID поста) для листания истории назад.

### Исправления

- `search_posts(channel_id=…)`: сейчас `in:<id>`, а Mattermost в `in:` ждёт
  имя канала — фильтровать по каналу правильно (по имени или по
  `channel_id` в результатах; выбор за исполнителем, проверить на
  реальном API-контракте).
- `get_mentions`: фильтр `since` применять до обрезки по `limit`.
- Поиск по нескольким командам: убрать дубли постов (DM/GM повторяются).
- `list_channels`: заполнять `unread_count` (в docstring обещан, сейчас 0).
- Упорядочивание результатов поиска — новые сверху, как в клиенте.
- `_enrich_posts_with_usernames` глотает все исключения — оставить мягкую
  деградацию, но не скрывать 401.

### Производительность

- `get_unread`: убрать N+1 `/channels/{id}` — имена каналов брать из списка
  каналов пользователя, полученного одним запросом на команду.
- Кэш в памяти с коротким TTL (порядка минуты) для: `me`, списка команд,
  метаданных каналов (муты, категории, имена). `search_posts`/`get_mentions`
  больше не обходят все каналы при каждом вызове.
- Запросы по нескольким командам — параллельно (асинхронный httpx с
  ограничением конкурентности), инструменты — `async`. Переход на async —
  решение по умолчанию; если по ходу окажется, что FastMCP и так гоняет
  синхронные инструменты в пуле потоков и async ничего не даёт, исполнитель
  может оставить sync + параллелизм в пуле.
- Кэш кэша кук (cookie host) и логика 401-перезапроса сохраняются.

### Упаковка и оформление

- Имя пакета на PyPI: **`mattermost-mcp-server`** (`mattermost-mcp` и
  `mcp-server-mattermost` заняты). Импорт-модуль остаётся `mattermost_mcp`.
  Консольные команды: `mattermost-mcp-server` (для `uvx mattermost-mcp-server`)
  и `mattermost-mcp` (совместимость).
- Версия 1.0.0. Описание пакета больше не «Read-only».
- `server.json` для официального реестра MCP (тип пакета pypi), маркер
  `mcp-name:` в README, как требует реестр для PyPI-пакетов.
- README переписать для сообщества: что это и чем отличается; quickstart с
  PAT (`uvx`); готовые конфиги для Claude Code (`claude mcp add`), Claude
  Desktop, Cursor, VS Code; таблица инструментов (чтение/запись); режим
  записи и модель безопасности; куки, cookie host и keychain — отдельным
  разделом «если PAT недоступны»; все переменные одной таблицей;
  troubleshooting (401, CSRF, прокси). Язык — английский.
- `CHANGELOG.md`, `CONTRIBUTING.md` (коротко), `SECURITY.md` (куда сообщать).
- CI: оставить матрицу тестов, добавить линтер (ruff) и workflow публикации
  на PyPI по тегу через trusted publishing (сработает, когда владелец
  настроит проект на PyPI).
- Удалить закоммиченные `__pycache__`, если они в git; `.gitignore` проверить.

## Решения, принятые мной (не владельцем)

- Конкретные имена переменных `MATTERMOST_ACCESS_TOKEN`, `MATTERMOST_AUTH_MODE`,
  `MATTERMOST_ENABLE_WRITE`.
- Имя пакета `mattermost-mcp-server` (владелец разрешил выбрать любое).
- Только stdio и uvx/PyPI; Docker и HTTP — вне рамок.
- Набор новых инструментов чтения и реакций; удаление — не делаем.
- Переход на async + кэш с коротким TTL.
- Версия 1.0.0, README на английском.

## Оставлено исполнителю

- Внутренняя структура модулей, именование внутренних функций.
- Точные TTL и лимит конкурентности.
- Способ исправить фильтр по каналу в поиске.
- Формулировки docstring и README (в рамках структуры выше).
- Тесты: на каждую новую ветку авторизации, защиту записи (инструменты не

  должны проходить без правок их ожиданий (кроме явно исправляемых ошибок).
